### 🗣️ 第一人称叙述约定（2026-06-08 修正）

**核心规则：** 当内容代表少爷的视角（如OfferPath详情页说明、成长主题卡片、申请叙事框架）时，**必须使用第一人称"我"**，而非第三方的"少爷"/"Joe"。

**两套视角的区分：**

| 内容类型 | 用词 | 示例 |
|:---------|:----|:------|
| **关于少爷的描述**（成绩变化、事件记录） | "他"、"少爷"、"Joe" | "少爷GPA达到3.91" |
| **少爷自己的表达**（愿景、计划、反思、故事） | "我"、"我的"、"我和老爸" | "我和爸爸一起创立的项目" / "我做这个不只是在创业" |

**⚠️ 容易忽略的地方：**
- 首页Profile卡片描述：「💻 创业项目 → Offer路书」✅（客观描述，不用改）
- 详情页标题：「💻 我的Offer路书 · 父子创业计划」✅（"我的"表视角）
- 阶段标题：「阶段一 · **我先打个基础**」✅（"我"字动作）
- 表格列名：「**我的角色** / **我要做什么** / **我能交出什么**」✅（第一人称行动）
- 老爸的话：不要写"家主提示：..."，而写"**老爸说：** ..."（家庭亲密感）

**例句对比例：**
```
❌ "少爷和家主共同创立的微信小程序项目——聚合藤校..."
✅ "我和爸爸一起创立的项目——把所有藤校...聚合起来"

❌ "发现留学信息不透明的真实痛点，与父亲一起创立..."
✅ "我发现留学信息不透明是很多家庭都会遇到的难题，所以我和老爸一起创立了..."

❌ "家主提示：这个阶段的重点是被动参与→主动发现"
✅ "老爸说：这个阶段最重要的是'别等着被分配任务，自己去找问题'"
```

### OfferPath作为爬藤背景提升方案（替代传统科创竞赛）

**核心判断：** OfferPath（Offer路书小程序）的爬藤价值**远超市面上任何科创班**，因为它是真实产品+真实用户+真实商业场景，而非一赛即止的竞赛项目。

| 对比维度 | 传统科创竞赛 | OfferPath实战 |
|:---------|:----------:|:------------:|
| 投入时间 | 额外每周6-8h上课 | **零额外时间（就是做项目的时间）** |
| 费用 | ¥3-5万/年 | **¥0（本就在做）** |
| 文书叙事深度 | "我设计X拿了Y奖" | "我发现了留学家庭的痛点，与父亲一起做出产品，服务了XX用户" |
| 面试独特性 | 每年数万中国学生有竞赛奖 | **极少高中生有上线产品+真实用户** |
| 技能习得广度 | 单一项目技能 | 全栈：产品思维+数据+技术+商业+项目管理 |
| 持续影响力 | 比赛结束即停止 | 用户越多影响力越大，持续增长 |

**少爷需要在OfferPath中建立的可讲述角色（选2-3个，不只是挂名）：**
- **产品经理**：定义功能优先级、基于"自己作为用户"的真实洞察

- **前端/全栈**：参与界面设计或交互逻辑

**风险防范：** 不能让MIT觉得"这是爸爸的项目，儿子挂名"。解决方式：

## 🚣 体育训练数据工作流

当用户发送赛艇训练数据（图片/截图/文档）时，按以下流程处理：

### 1. 图片保存
```bash
mkdir -p /root/joe-growth-tracker/assets/images/YYYY-MM-DD/
cp <缓存路径> /root/joe-growth-tracker/assets/images/YYYY-MM-DD/<描述性文件名>.jpg
```
- 文件名用英文+描述性短命名（如 march-training-record.jpg、2km-rowing-splits-june2.jpg）
- 同时复制到 joe-growth repo 的 assets 目录

### 2. 数据提取
从图片中识别并提取：

**产出形式：**

**用户数据提供模式（典型对话模式）：**
用户可能以碎片化方式逐步提供费用信息，每次只给一条。需要将每次添加的内容追加到 expense-ledger.md 的对应年份条目中，并同步更新 累计表 和 记忆中的汇总数字。

**⚠️ 数据敏感度注意：**
- 费用金额可在子焘记原始日志中记录
- 发布到公开的 GitHub Pages 网站时，费用数字应做模糊处理或仅展示趋势不展示具体金额

**⚠️ 费用确认礼仪（Expense Confirmation Protocol）：**

当用户提供费用信息时，务必确认清楚以下三点，避免后续修正：

1. **性质确认：** "这是学费还是赛艇开支？"（区分 TU 和 ROW）
2. **精确度确认：** "是精确数字¥24,000还是约¥2.4万？"（影响TBD标注）
3. **归属确认：** "这是哪一年的开支？"（影响年份归类和累计表）

**⚠️ 学年 vs 日历年混淆陷阱（Academic Year Pitfall — 2026-06-19）：**

当用户说"改XX年的学费"时，**"XX年"通常指学年（Academic Year）而非日历年（Calendar Year）**。例如"2025年初三学费"实际指"2025-2026学年"，横跨2025和2026两个日历年份，两个年份的学费都应更新。

**标志性对话模式（实际教训）：**
```
用户: "2025年初三的那个学费由25万改为30万"
我理解: 🔴 只改了2025年日历年的学费
用户实际意思: ✅ 2025-2026学年的学费，即2025年和2026年都从25万→30万
```

**如何避免：**
- 听到"XX年学费"时，确认是"XX学年（通常跨两年）"还是"XX日历年"
- 检查：前端页面、education-expenses.md、expense-ledger.md 中相关年份的学费是否都要改
- 如不确定，直接问用户："您说的是 2025-2026 学年（含2026年）还是只改2025年？"
- 如果用户说完整说法如"2025年初三的学费"，默认2025和2026均为该学年段——初三通常是跨年学年

**🔑 关键规则：学费 vs 体育必须严格分离**

用户提供的所有费用数字，不能默认合并为"教育总投入"。需要区分为两条独立的流水：
- **学费（TU）**：学校学杂费，记入 education-expenses.md
- **体育/其他（ROW/TEST/STEM/HOBBY/OTHER）**：赛艇训练、比赛、培训、夏令营等，记入 expense-ledger.md
- **累计数字不能合并**：学费252万和赛艇+其他=267万+是两条不同口径的总计

**⚠️ 典型修正事件（经验教训）：**
去年某次录入时，按照以下数字构建账本，后被用户逐一批驳：
1. ~~光华剑桥美高学费¥50万~~ → 纠正为 **¥25万/年**（用户："是25万不是50万"）
2. ~~将赛艇费用计入"教育总投入"~~ → 需分开为 **学费 + 赛艇专项** 两列
3. ~~¥302万累计~~ → 纠正为 **学费252万 + 赛艇/其他=267万** 两个口径

**从这些修正中学到的：**
- 第一次记录时就要问清楚该费用的性质（TU/ROW/OTHER）
- 默认不要合计不同类别的费用到一条累计线上
- 累计总计要标注口径："¥267万+（含学费252万+赛艇/其他）"而不是"¥267万（总投资）"
- education-expenses.md 和 expense-ledger.md 是两个独立文件，各有自己的累计表，不能共用同一个数字

### 8. 多层记录工作流（Multi-Layer Recording）

当用户一次性提供多种信息（日程变更 + 财务数据 + 成绩数据 + 目标设定）时，按以下三层记录，缺一不可：

```

        持久化存储，确保任何会话都能回忆
        记录：日程变更、费用数据、成绩基线、项目清单
```

```
用户纠正 → 找出所有引用了该数字的文件 → 逐个修正 → 验证关联数字
```

**⚠️ 先确认再批量修改（Confirm Before Mass-Edit — 2026-07-21 实战教训）：**

### ⏰ 时间校准规则（Time Calibration — 2026-06-08 用户强调）

**每次记录带日期的条目前，必须用 `date` 命令确认当前真实日期。** 不得假设或沿用会话上下文中可能已过时的时间戳。


**常见错误模式：**
- ❌ 沿用上一会话/上下文窗口中的日期（可能已过了一天）

### 🔄 万能验证工作流（Universal Verification Workflow — 2026-06-19 确立）

> **核心信条：不信任"只改了一个地方"。每次更新都必须证明——而不是假设——所有地方都对了。**

任何更新（费用录入、数据修正、页面改动、获奖导入、日程变更）完成后，必须执行以下**全栈全通道验证链**：

**Step 1 → 全分支检查：**
- `git branch -a` 列出所有分支
- 检查 main 和 gh-pages 的 `data.js`（或其他修改的文件）内容一致
- `git show <branch>:<file>` 逐分支确认

**Step 2 → 全文件检查：**
- 列出本次修改涉及的所有关联文件清单
- 逐项确认每个文件都已同步更新（不止主文件）
- 特别注意：expense-ledger.md 两处副本、data.js 两分支、index.html 多页面
- **⚠️ "旁观者漂移"陷阱（Bystander Drift）：** 即使这次只改了某几年的数字，也要顺便检查**相邻年份**的静态值是否与 data.js 一致。实际发生过2023年金额（data.js=¥328,000 → index.html静态=¥300,000）因无人触及而长期漂移的情况。每次修改任意年份数据时，用 grep 扫一遍 index.html 中 `expense-year-20XX` 的静态值是否大致对齐 data.js。
- **search_files 多格式覆盖：** 搜索旧数字时，不能只搜一种格式。必须同时搜索带逗号、不带逗号、带¥符号三种变体：
  - data.js 注释用 `¥400,000`，JS 数值用 `400000`，HTML 用 `¥250,000`
  - 漏掉任何一种都会给出"已全部清除"的误报
  - 推荐：`grep -rn '250,000\|250000\|¥250,000' .` 三合一搜索

**Step 3 → 推送：**
- main 分支 push
- gh-pages 分支 push（如果涉及网页展示内容）
- ⚠️ **更新验证脚本**：如果本次改动改变了验证脚本 `scripts/verify-expense-deployment.sh` 中的硬编码检测数字（2024/2025/2026 金额、总投入显示、页面检查项），**必须在推送前同步更新脚本**，否则下次验证会报错。
- 等待 1-2 分钟让 GitHub Pages CDN 缓存刷新

**Step 4 → 浏览器可视化验证（最关键！不可省略）：**\n- 用 `browser_navigate` 打开网站相关页面\n- 用 `browser_vision` 截图确认数字/内容显示正确\n- 肉眼核对：首页数字、详情页数据、明细表\n- 验证示例：总投入显示 ¥295万+（不是 ¥290万+）、2026年显示 ¥353,652（不是 ¥306,261）\n- **⚠️ GitHub Pages CDN 延迟**：推送后可能需要 1-10 分钟 CDN 才刷新。如果 browser_navigate 超时或页面显示旧数据，用备用方案：\n  ```bash\n  # 1. 直接 curl 抓取 data.js 确认部署内容\n  curl -sL https://joeweiyuan.github.io/joe-growth/data.js | grep -E "202[4-6]:"\n  \n  # 2. 用 node 快速验证 JS 自动计算是否正确\n  node -e "\n  const years = {2015:110000,2016:110000,2017:200000,2018:220000,2019:240000,\n                 2020:220000,2021:240000,2022:248000,2023:328000,2024:428000,\n                 2025:328400,2026:353652};\n  const total = Object.values(years).reduce((s,v)=>s+v,0);\n  console.log('总计:', total.toLocaleString(), '→ ¥' + Math.floor(total/10000) + '万+');\n  "\n  # 3. 确认 data.js 中关键年份数字正确\n  curl -sL https://joeweiyuan.github.io/joe-growth/data.js | grep -oP '2024: [0-9]+|2025: [0-9]+'\n  ```\n- 如果 data.js 已是最新但页面仍显示旧数据 → 说明 CDN 尚未刷新 → 等待 2-5 分钟再验证 → 仍不对则检查 index.html 中的静态备选数字（旧硬编码值覆盖了 JS 渲染）
- 如需自动化验证，可运行内置脚本：`bash scripts/verify-expense-deployment.sh`

**Step 5 → 向用户汇报验证结果：**
- 明确说"已确认网站显示正确"（附截图/数字证据）
- 如发现问题，立即回溯修复

**⚠️ 批量文本替换（sed级别）的隐形陷阱：** sed只改当前分支。用 `sed -i` 全局替换了 main 分支后，gh-pages 分支完全不受影响——需要**显式切换到 gh-pages 分支重新执行同样的 sed 命令**。详见 `references/bulk-text-replacement.md`。

**⚠️ 常见遗漏：**
- ❌ 改完数据不推 gh-pages（网站不更新但以为更新了）
- ❌ 推完不验证，以为一定对（结果 CDN 卡缓存或格式问题）
- ❌ 只验证首页不验证详情页（费用详情页可能还是旧数据）
- ❌ 只验证一个数字不验证关联数字（总投入变了但各年合计没同步）

**常见疏漏：**
- ❌ 只改了 daily-logs markdown，忘了改 index.html 中的对应 HTML 片段（时间线/月度叙事/费用/获奖等）
- ❌ 只推了 main，忘了推 gh-pages（网站不更新）

**💡 技巧：当需要清除大量散布的HTML内容时，直接重写整个 index.html 比逐个 patch 更可靠**\n- 如果 patch 因转义字符/JSON 编码匹配失败，或用 patch 需要 5+ 次调用时\n- 直接用 write_file 重写完整的 index.html 确保零残留\n- 重写前先用 read_file 读出完整内容，在此基础上修改再写回\n\n**⚠️ patch 工具在 Markdown 表格中的陷阱（两类症状）：**

**症状 A — new_string 多出 pipe：** 用 `patch` 修改 Markdown 表格行时，new_string 开头容易多写一个 `|`（写成 `||`），导致表格多出一列。每次改完后检查 diff：新行应该以 `|` 开头，不是 `||`。如果发现，立即用第二次 patch 修正。

**症状 B — old_string 因 pipe 无法唯一匹配：** 当 old_string 包含 pipe 字符（如 `| 已推送简版提醒 |`）时，patch 工具的模糊匹配会因多个表格行结构相似而返回"Found N matches"。此时用 `replace_all=true` 配合**尽量短的该行独有子串**（如某条记录的独特日期 `2026-07-10` 而非整行），再分步修复替代行为产生的差异。推荐策略：先改日期字符串本身，再分两三次 patch 修完碎片化的改行。

**⚠️ 关键陷阱：验证活动归属**
- .ics 日历中可能包含**非少爷**的活动（如家族成员的课程/活动），切勿自动假设所有条目都属于 Joe

- 主动向用户确认活动归属（"这是少爷的还是家主母的？"）比先录后删更高效

**⚠️ gh-pages cherry-pick 冲突处理模式：**
当两个分支（main 和 gh-pages）内容差异较大时，直接 `git cherry-pick main` 会因文件冲突而失败（尤其是已被部分清理的 gh-pages 分支）。

**安全做法：**
```bash
# 1. 在 gh-pages 分支做完整文件覆盖
git checkout gh-pages
git checkout main -- .    # 用 main 的所有文件覆盖 gh-pages
git add -A
git commit -m "sync main: 更新说明"
git push origin gh-pages
# 2. 切回 main
git checkout main
```

这样做会丢失 gh-pages 上独有的文件（如果有），但保证了网站部署分支与源码分支的一致性。如果 gh-pages 上有需要保留的特殊文件（如 CNAME），要手动恢复。

**更安全的方式（只同步 index.html 等关键文件）：**
```bash
git checkout gh-pages
git checkout main -- index.html data.js milestones.md  # 只覆盖特定文件
git add -A
git commit -m "同步main: 更新说明"
git push origin gh-pages
git checkout main
```
- GitHub Pages 推送后最多需要10分钟 CDN 缓存才能刷新
- 推送后立即检查网站，可能仍显示旧版本 → 这是预期行为
- 等待2-5分钟后用 curl -sL <url> 重试验证
- 如果用户截图反馈网站内容未更新，直接说明CDN延迟而非怀疑部署失败

**🔍 视频内容快速检查（Video Frame Inspection — 2026-07-21，2026-08-07 增强）：**

用户发来视频时，不要猜测内容。流程：**ffprobe 拿元数据 → 多时间点抽帧 → vision_analyze 数帧 → 带时间戳定位少爷**。

```bash
# Step 1: 元数据（时长/分辨率/码流）— 决定抽几个点
ffprobe -v quiet -print_format json -show_format -show_streams <视频路径> | head -60

# Step 2: 按 ~5 秒间隔抽帧（65秒视频抽 13 帧；长视频间隔放大）
for t in 1 5 10 15 20 25 30 35 40 45 50 55 60; do
  ffmpeg -v quiet -ss $t -i <视频路径> -frames:v 1 -q:v 2 /tmp/frame_${t}s.jpg -y
done

# Step 3: 挑 3-4 个代表帧（开头/中段/结尾）批量 vision_analyze
# 问题模板："这是什么场景？画面里有什么（人/船/河/建筑/动作）？
#            有没有穿白色短袖黑色短裤的亚洲男孩（少爷）？在什么位置？"
```

- **多帧采样优于单帧**：单帧只能判断场景类型；多帧能定位人物在视频中的**出现时段**（如"2秒处码头人群右侧中部=少爷，63秒处赛艇馆前再次出镜"），写进 daily-log 的影像表格时带时间戳，证据力更强
- 抽帧能区分：室内展厅/码头准备/水上训练/教练讲话/通勤班车等不同场景
- 单帧描述模糊（vision 报告"无法准确判断"）时，**换帧重试**或放大局部——分辨率低时让 vision 描述"人群着装颜色分布"再人工比对
- 视频归档条目格式（US tour 实战定型）：表格行写明 **时长/分辨率 + 场景链（集合→教练讲话→码头下水准备）+ 少爷时间戳定位**

**⚠️ 人物识别陷阱（Who-is-Joe Pitfall — 2026-07-21 实战教训）：**

在合影中判断哪个是少爷时，**不要凭身高/站位猜测并自信断言**。实际教训：误认"最右条纹Polo高个"为少爷，用户纠正"右二是穿白衣服的"。规则：
- 识别不确定时，标注位置描述（"右二白色短袖"）并注明"待确认"，让用户确认
- 用户确认后立即修正 daily-log 描述 + 同步推送 GitHub（tracker 版和 joe-growth 版都要改）
- 绝不用"最右高个就是少爷"这类确定性表述覆盖不确定性

**✅ 穿搭签名法（Outfit Signature — 2026-08-07 实战验证）：** 一旦某张照片中少爷的**位置已由用户确认**（如 MIT 码头合影"右二白短袖黑短裤"），这套**穿搭就是后续识别的可靠锚点**：同站/相邻站的新照片、视频抽帧中，优先按"白短袖+黑短裤"在人堆里找对应人物，命中后位置描述直接写"白短袖黑短裤=少爷"（如达特茅斯视频 2秒/63 秒处同款确认出镜）。注意：仅限**同一行程段内**有效（行李少、衣服轮换有限）；跨站/隔天若出现疑似同款但不确定，仍回到"待确认"流程。

**⚠️ 穿搭签名法 vs 肤色/种族信号冲突（2026-08-13 实战修正）：** 宾大九人大合影中，穿搭签名指向"左五白T黑短裤"，但 vision 判定"左四深蓝T棕短裤=晒得最黑的亚洲少年"，用户确认**左四是少爷**——衣服在多日行程中会换（同一天码头合影白T、船库合影深蓝T）。教训：
- 当穿搭信号与 vision 的**肤色/种族/晒痕信号冲突**时，肤色信号优先列为候选（晒黑是连续过程，衣服会换）
- 最终仍以**用户指认为准**，确认前一律标"待确认"
- 同一行程段内少爷可能有多套衣服，"签名法"只在同一天内高置信

**⚠️ 建筑标志/字母 OCR 陷阱（Logo OCR Pitfall — 2026-08-13 实战教训）：** vision 分析建筑标志/地面喷绘标志时，容易把字母看错（实战：宾大 Burk-Bergman Boathouse 地面红**"P"**（Penn 首字母）被 vision 误读为"R"，家主纠正）。规则：

- 涉及大学/机构标志时，可先按常识校验（Penn=P、Princeton=虎、MIT=MIT 等）
- 用户纠正后立即修正 daily-log（tracker + growth 双副本）+ 推送 GitHub

**🔧 解析 .xlsx 文件（无 openpyxl 时的方案）：**

当系统 Python 无法安装 openpyxl 时，使用 Python 内置的 zipfile + xml.etree.ElementTree：

```python
import zipfile, xml.etree.ElementTree as ET

with zipfile.ZipFile(path) as z:
    # 1. 解析 sharedStrings.xml 获取文本映射
    tree = ET.parse(z.open('xl/sharedStrings.xml'))
    shared = {i: ''.join(si.itertext()) for i, si in enumerate(tree.getroot())}
    
    # 2. 解析 sheet1.xml
    tree = ET.parse(z.open('xl/worksheets/sheet1.xml'))
    ns = {'s': 'http://schemas.openxmlformats.org/spreadsheetml/2006/main'}
    for row in tree.getroot().findall('.//s:row', ns):
        vals = []
        for c in row.findall('s:c', ns):
            v = c.find('s:v', ns)
            t = c.get('t', '')
            if v is not None and v.text:
                if t == 's':
                    vals.append(shared.get(int(v.text), v.text))
                else:
                    vals.append(v.text)
            else:
                vals.append('')
```

## 柱状图移动端渲染陷阱（续）——2026-06-08 实战定型参数

**容器尺寸（经5轮调整定型）：**
```html
<div id="toefl-target-chart" style="display:flex;align-items:flex-end;gap:4px;height:110px;padding:18px 0 6px 0"></div>
```
- height: 110px（固定高，min-height 会撑太高）
- padding: 18px 0 6px 0（顶部 18px 不压标题，底部 6px 不浪费）

**标题 h2 配合：**
```html
<h2 style="font-size:.95rem;margin:0 0 12px 0">🅰️ 提分计划</h2>
```
- margin:0 0 12px 0 移除浏览器默认 h2 上边距（约13px），标题紧贴卡片顶

**布局顺序（分数在🎯上面——放柱体内会重叠）：**
```
分数（font-size:.78rem, font-weight:600, margin-bottom:3px, white-space:nowrap）
🎯 图标（font-size:.65rem, color:var(--gold), min-height:14px, margin-bottom:4px, line-height:1）
柱体（width:60%, min-width:24px, border-radius:4px 4px 0 0）
标签（font-size:.65rem, margin-top:4px, text-align:center, line-height:1.2）
```

| 间距值 | 效果 | 适用 |
|:------|:----|:----|
| gap: 8px | ❌ 超宽，4列溢出屏幕 | 别用 |
| gap: 4px | ✅ 正好容纳4列 | **推荐** |
| gap: 0px | ❌ 文字和图标重叠 | 别用 |
| padding-top: 24px | ❌ 太高 | 别用 |
| padding-top: 18px | ✅ 不重叠、刚好 | **推荐** |

**迭代教训（5轮调整才稳态）：**
1. 分数🎯重叠 → 分数移出柱体到🎯上面
2. 分数压标题 → h2 margin-top:0 + chart padding-top:20→24→18px
3. 柱状图太高 → height 100px→min-height→110px（固定）
4. 柱体圆角 6px→4px, min-width 28px→24px
5. 最终稳态：h2 margin:0 0 12px 0 + chart height:110px, padding:18px 0 6px 0, gap:4px\n\n---\n\n## 📊 输出格式样例

## ⚠️ 重要规则

### 1. 忠实记录，不编造
- 只记录确认发生过的事
- 不美化、不夸大、不编造
- "信号提炼"和"文书素材建议"是基于事实的解读，不是虚构

### 2. 保护隐私与公开的平衡
- 原始日志（daily-logs/）内容详细、含家庭内部细节 → **仅限本地，不上传到 GitHub Pages**
- GitHub Pages 网站（index.html）展示的是**精炼后的叙事版本**（curated/、themes/、milestones）→ 公开可访问
- 发布到网站的内容已做了提炼和去敏感化，不包含原始日志的私密细节
- 升学文书使用时需基于事实素材重新创作
- 网站内容仅包含已核实、可对外展示的成长叙事

### 3. 格式自由，但索引必须更新
- 输入格式不限制
- 但每次输入后必须更新 growth_index.json

### 4. 累积效应
- 单条日志可能看起来微不足道
- 但3个月、6个月、1年之后，累积的素材就是最真实的成长轨迹
- 保持持续记录，不因"今天没什么特别的"而跳过

### 5. 多方输入
- 爸爸、Alice、Joe自己都可以输入
- 不同视角的记录更有价值
- 每条记录标注记录人

### 6. 网页/一页图 PNG 渲染：必须用脚本，禁止手写 chromium 参数（2026-09-30 事故）
- **事故**：`mit-roadmap.html` 的 CSS 里 `body { width: 1680px }`，但手写命令用了 `--window-size=1280,...` → **页面右侧 400px（约 24%）整块被裁掉**，图发到群里才发现，且已提交/上线（错的 PNG 3360×5513 被当"完整图"推了 4 小时）。
- **根因**：headless chromium 的截图宽度 = 窗口宽 × 像素密度，窗口宽 < 页面固定 body 宽时右侧直接消失；`--hide-scrollbars` 让"有内容被裁"更难肉眼发现。
- **铁律**：渲染一页图**只用** `python3 scripts/render_page_png.py <html> <out.png> --min-width <页面CSS宽>`。脚本会自动从 CSS 解析 body 宽度、按该宽度渲染、裁掉空白，并**物理校验**：右/左边缘列必须纯背景、内容右侧留白 ≥10px、宽度 == body宽×dsf —— 任一不过即退出码非 0 + 报错，**禁止发布**。校验已有图：`--check-only <png>`。
- **snap 坑**：`--screenshot=` 只能传 `/tmp/xxx.png`（snap 内 /tmp 被映射到 `/tmp/snap-private-tmp/snap.chromium/tmp/`；传私有 tmp 绝对路径会静默不写文件）。
- **收尾三问**（发图前自查）：① 图宽是否 = 页面 CSS 宽 × dsf？② 最右列是否纯背景？③ 发出去前是否至少读过底部/右侧局部？
